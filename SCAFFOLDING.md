# OneTerminal Scaffolding — Implementation Plan

## Overview

One scaffolding tool:

1. **`npm create one-terminal`** — scaffolds a complete OneTerminal monorepo workspace

Templates are **never hand-edited**. A `scripts/extract-templates.ts` extractor derives all
`.ejs` template files from the live apps. CI enforces this: any PR that modifies `apps/` must
also commit updated templates (or the drift check fails).

An **upgrade command** (`npx create-one-terminal upgrade`) applies framework migrations to
already-scaffolded projects.

---

## Architecture at a Glance

```
one-terminal/
├── packages/create-one-terminal/   ← npm package: "create-one-terminal"
│   ├── src/
│   │   ├── index.ts                ← CLI entry — routes create vs upgrade
│   │   ├── create/                 ← scaffold a new workspace
│   │   ├── upgrade/                ← migrate an existing workspace
│   │   └── merge/                  ← config/dep merge helpers
│   ├── templates/                  ← GENERATED by extract-templates.ts
│   └── versions.json               ← migration manifest (bundled + published)
├── scripts/
│   ├── extract-templates.ts        ← derives templates/ from live apps
│   └── check-template-drift.ts    ← CI: diff extracted vs committed
└── .github/workflows/
    ├── template-drift.yml          ← runs on every PR touching apps/
    └── publish-scaffolder.yml      ← publishes on git tag
```

### Key design decisions

- **EJS** (`.ejs`) for templates — no conflict with `{{` in Rust format macros or JSON
- **Apps are source of truth** — templates extracted, never authored by hand
- **`smol-toml`** for TOML parse/write — pure ESM, zero deps
- **`@clack/prompts`** for all interactive UI
- **Node 18+ `fs/promises`** only — no `fs-extra`
- `create-one-terminal` is unscoped on npm (required for `npm create one-terminal` to resolve)

### Conditional blocks (`ot:if` annotations)

Lines in live source files annotated with `# ot:if <var>` (TOML) or `// ot:if <var>` (Rust/TS)
are wrapped in EJS conditionals by the extractor:

```toml
# source (Cargo.toml)
ot-fdc3  = { path = "packages/ot-fdc3" }  # ot:if includeFdc3
```

```ejs
# extracted template
<% if (includeFdc3) { %>
ot-fdc3  = { path = "packages/ot-fdc3" }
<% } %>
```

### Static files (never templated, no `.ejs` extension)

Copied verbatim — no substitution applied:

- `src-tauri/build.rs`
- `src/vite-env.d.ts`

### Binary files

Copied with `fs.copyFile()` — no `.ejs` extension:

- `src-tauri/icons/*.png`
- `src-tauri/icons/*.ico`
- `src-tauri/icons/*.icns`

## Phase 4 — Upgrade CLI (`src/upgrade/`)

### Version tracking

The scaffolded `package.json` gets:

```json
"oneTerminal": { "version": "0.1.0", "scaffoldedAt": "2026-05-03" }
```

### `versions.json` manifest

Bundled in the npm package at `packages/create-one-terminal/versions.json`.

Schema:

```ts
interface VersionEntry {
  version: string; // semver
  releaseDate: string; // ISO 8601
  breaking: boolean;
  changelogUrl: string;
  migrations: MigrationSpec[];
}

type MigrationSpec =
  | { type: "config-merge"; target: string; patch: Record<string, unknown>; description: string }
  | {
      type: "dep-bump";
      target: string;
      deps: Array<{ name: string; ecosystem: "cargo" | "npm"; newVersion: string }>;
      description: string;
    }
  | { type: "structural"; target: string; operations: PatchOperation[]; description: string };

type PatchOperation =
  | { op: "insert-after-line-matching"; pattern: string; content: string }
  | { op: "replace-line-matching"; pattern: string; replacement: string }
  | { op: "add-file"; sourcePath: string; targetPath: string };
```

### `_managed` annotations in config files

The scaffolded `agent.config.json` and `terminal.config.json` include a `_managed` array
listing framework-owned field paths. The upgrade tool only writes to `_managed` fields.
User-modified managed fields trigger the conflict handler.

```json
{
  "_managed": ["appDirectoryUrl", "engineCatalogUrl", "ports.tcpBroker", "ports.fdc3Bus", "ports.dacpBridge"],
  "title": "MyApp Desktop Agent",
  ...
}
```

### Upgrade command flow

1. **Validate** — read `package.json → oneTerminal.version`; abort if missing
2. **Fetch manifest** — try npm registry JSON; fall back to bundled `versions.json`
3. **Build chain** — all versions with `semver > current`, sorted ascending
4. **Confirm** — show migration summary table; prompt to proceed
5. **Snapshot** — copy all target files to `.one-terminal/upgrade-backup-<version>/`
6. **Execute** — apply each migration; conflict handler fires on `_managed` field user-modifications:
   - `auto` — apply framework value
   - `skip` — keep user value, log to report
   - `merge` — write `.merge` file with git conflict markers
7. **Update version** — write new `oneTerminal.version` to `package.json`
8. **Write report** — `upgrade-report.md` at project root (applied / skipped / needs-manual)
9. **Rollback** — if any migration throws, restore all files from snapshot
